# Web 管理端三类角色界面设计

> 2026-09-29 本地后端接口已按 [BACKEND_COMPLETION_PLAN.md](./BACKEND_COMPLETION_PLAN.md) 落地；综合回归、数据库 seed 同步和 Web 联调仍待验收。下文菜单按当前代码权限编排，生产权限是否生效须以受控同步结果为准。

> 状态：产品与交互设计，尚无 Web 页面实现。依据《查课管理系统V1.0建设说明》（V1.01 合并版）、`docs/PERMISSIONS.md` 与当前后端 API。页面入口按 `/api/v1/me.permissions` 组合显示，不按角色名称写死三套应用；多角色账号取有效权限并集，后端继续判定数据范围和资源归属。

## 共用框架

所有管理账号共用登录页、顶部“当前学期 / 第几周 / 当前账号”、左侧业务导航、主工作区和任务详情抽屉。首页首先展示以**日期—节次**为轴的查课工作表，再展示该角色能处理的待办；这比通用四张 KPI 卡更贴合学院按周查课的工作方式。列表的五种当前状态保留文字标识，另设独立的“截止时考核”列，不能把补交后的当前状态覆盖历史“逾期未执行”事实。筛选使用学期、周次、日期、班级、课程、状态；管理负责人看到当前学院全部年级，不设置逐人年级过滤。

建议视觉基线：深蓝 `#20344A` 用于导航，纸白 `#F7F9FB` 用于工作区，青蓝 `#176B83` 用于主要操作，琥珀 `#B56B12` 用于待处理/逾期，砖红 `#B4463A` 用于异常/拒绝，墨色 `#24313D` 用于正文。周次轴、节次刻度和明确的表格线承担主要辨识度；状态必须同时有文字和颜色，不依赖颜色辨认。数据密度以桌面浏览器为主，窄屏转纵向卡片；保留键盘焦点与低动态效果。

### 学生工作负责人：查课与排班台

首页顺序：本周课次选择与任务下发 → 志愿者排班和人工调整 → 学院考勤周报 → 学生与考勤查询。负责人必须绑定有效学生身份；解绑或学生停用后后端撤销负责人角色与可选授权。个人获得 `objection.initial_review` 才增加“待初核”，获得 `statistics.read` 才增加统计与未完成清单。两项可选权限默认关闭，不把“无权限”写成“暂无数据”。

| 页面 | 默认可见的操作 | 不能出现的操作 |
| --- | --- | --- |
| 查课任务/排班 | 全学院各年级查看；精确选择课次、预览/生成、自动排班、人工改派、取消与安全恢复 | 修改日截止、提交审核 |
| 学生与考勤 | 搜索学生、查看当前考勤及认定版本 | 更正考勤、调整应到人数、审核提交 |
| 身份绑定 | 按学号查人、线下核验后签发/作废一次性码、解绑/换绑 | 角色分配、修改教师账号 |
| 异议初核（可选） | 查看异议/证明、通过或驳回初核；处理后仍展示待终审 | 终审、直接更改考勤 |
| 统计（可选） | 班级/课程/未完成统计 | 不因统计权限取得其他写权限 |
| 周报 | 学院考勤周报主记录、版本历史、生成与下载 | 班级周报（`CLASS` 请求 422） |
| 课程课表 | 查询、导入课表和 XLSX 导出 | 名单/志愿者资格导入及学期/校历维护 |

学生工作负责人拥有 `academic.read`，但没有 `academic.manage`、`submission.review` 或 `audit.read`；不提供学期/校历维护、提交审核和审计页面。

### 教师管理员：业务执行台

首页顺序：待处理任务（未分配/待审核/已逾期）→ 本周查课工作表 → 快捷动作“选择查课范围”“自动排班”“处理提交”→ 异议终审 → 统计与周报。任务生成页采用“正向勾选需查班级/课程 → 预览 → 确认生成”；筛选变化不丢失已勾选班级，生成后进入排班结果页，明确列出未分配原因和人工处理入口。

教师可进入基础数据、两步导入、任务生成、排班调整、调班申请审核、截止管理、提交审核、应到调整、考勤更正、异议初核/终审、统计和周报。管理侧提交列表/详情读取 API 已落地，页面应调用 `/management/submissions`。周报仅提供学院考勤汇总；版本列表显示生成者、原因、最终更新时间及源数据落后提示。

教师的“人员权限”页分两部分：角色分配从现有账号中选择已绑定有效学生的目标，仅能增删 `STUDENT_AFFAIRS_MANAGER`，提交完整角色集合时必须保留目标已有的其他角色；可选授权页则仅列出负责人，逐人开关 `statistics.read`、`objection.initial_review`。当前角色目标接口返回全部账号，前端须以服务端的绑定校验为准；不能将列表描述成已具备多学院隔离。保存使用目标 `lockVersion`；409 时刷新并重新确认。

### 超级管理员：治理与业务台

业务页与教师管理员共用，不额外复制一套查课功能。首页在业务待办之外增加“账号与权限变更”“审计与配置”区；这些区块只有对应读取 API 完成后才展示实际记录，不用静态数字冒充系统监控。

超级管理员的人员页增加教师账号创建、停用、管理重置口令与角色授权，可管理负责人两项可选权限。角色操作仍基于后端目标选择器、完整角色集合及版本号；危险操作显示目标账号、增删的角色差异和影响说明，确认后读取最新权限。超级管理员也不能替志愿者提交查课事实，不能替学生提交异议。

审计页仅超级管理员可见，后端已有有界列表与详情 API，before/after 仅返回白名单字段；系统配置仍没有通用可写 API。已有的“日截止”是独立业务配置，可由具备 `submission_deadline.manage` 的教师/超管在业务页操作；负责人只能读取。

## 权限到菜单与按钮的落点

| 功能 | 入口条件 | 修改按钮条件 | 当前接口边界 |
| --- | --- | --- | --- |
| 任务/排班 | `inspection.read` | `inspection.generate`、`assignment.manage`、`inspection.cancel` 分别控制 | 读写现有；状态与截止考核由服务端返回 |
| 学生/考勤 | `student.read`、`attendance.read` 分别控制 | `student.manage`、`attendance.correct`、`attendance.expected_count_adjust` 分别控制 | 当前认定与版本独立展示 |
| 绑定 | `identity.binding.manage` | 同权限，提交时需要线下核验确认 | 签发、作废、解绑 API 已有 |
| 提交审核 | `submission.review` | 同权限 | 管理读取列表/详情已落地，待 Web 联调 |
| 异议 | `objection.initial_review` 或 `objection.final_review` | 初核/终审分别判定；终审改判另需 `attendance.correct` | 异议列表/详情与处理已有 |
| 统计 | `statistics.read` | 无 | 与 `report.read` 独立 |
| 周报 | `report.read` | `report.generate` 才显示生成 | 主记录发现已落地；仅学院考勤汇总，`CLASS` 返回 422 |
| 人员角色/可选授权 | `role.assign` 或 `optional_permission.manage` | 目标选择器和版本检查进一步收窄 | 教师只操作负责人角色 |
| 审计/系统配置 | `audit.read`、`system.config.read` | `system.config.manage` | 审计读取已落地；通用系统配置写入未落地 |

多角色账号允许菜单并集；涉及本人学生/志愿者事实的页面仍由有效绑定及后端 OWN 范围约束。权限变化后下一次请求按后端判定，前端遇 403 立即刷新 `/me` 和菜单，不因旧页面缓存继续展示敏感数据。

## 后端权限复核（2026-09-29）

- 当前分支 `dev-main`，身份策略 `backend/app/modules/identity/policy.py` 中，教师角色变更差集只能包含 `STUDENT_AFFAIRS_MANAGER`；`IdentityService.assign_roles` 在事务内重读角色后强制执行该限制。教师不能增加或撤销教师角色；同时持有 `SUPER_ADMIN` 的账号按超管分支允许。
- 超管已有 `/teacher-accounts` 创建、停用和管理重置口令入口；教师管理员不能创建或停用教师账号。本人密码账号可调用 `/me/password-change`。
- 角色目标列表与可选权限目标列表不同：前者目前返回全部账号，后者仅返回负责人。可选权限接口拒绝对自己进行任何开关操作，包括关闭。
- 可选开关只管理个人授权。教师同时兼任负责人时，即使关闭某项个人授权，也不会移除教师角色自带的相同权限；界面须区分“个人授权”与“最终有效权限”。
- 当前补全后的后端单元测试 163 项通过；综合 MySQL 回归仍在执行，数据库 seed 同步和生产权限不由前端设计文档证明。页面联调以最终验收结果为准。

## 共同交互约束

- 空列表说明所选条件下无记录；无权限说明权限不足；加载失败提供重试。三个状态不用同一句“暂无数据”。
- 签发材料短时链接时调用 `/files/{id}/access`，不长期缓存签名 URL，不把证明内容写进前端日志。
- 列表筛选、分页保留在 URL 查询参数，便于回到同一工作位置；业务 ID 始终是字符串。
- 所有写操作先读取当前版本；409 重新取数并显示“数据已更新”，用户确认后再提交。前端隐藏按钮只是交互，后端仍做权限与范围校验。
