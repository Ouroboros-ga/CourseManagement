# GPT 主导、低成本模型执行的交接工作流

## 目的与适用范围

GPT/ChatGPT 承担主模型、思考、协调和最终质量责任，并亲自写复杂、高要求的代码与内容。低成本模型负责有明确输入、编辑范围和验收标准的工程执行。降低的是重复阅读、重复规划和机械实现成本，不把关键判断或最后验收转交给小模型。

**触发规则：默认 GPT 直接完成工作，不主动调用任何子 agent。只有用户明确询问或要求拆分、委派或任务书时，才生成交接包；一般开发、修复、审查请求不触发。生成交接包不授权启动 agent 或自动投递，调用须有用户对应的明确要求。过去的并行许可不作为后续任务的持续授权。**

该工作流适用于当前项目，不绑定具体产品、API 或模型。第三方入口和具体模型尚未配置，默认由用户手动把任务包交给 OpenCode、Claude Code（若为用户所指工具）、WorkBuddy、Trae 等。产品名称不等于模型，工具之间也不默认共享会话、技能、文件或凭据。

## 分工与任务筛选

| 工作 | 默认负责人 | 原因 |
| --- | --- | --- |
| 需求、架构、权限身份、事务/并发、跨模块规则、复杂交互、高要求文档 | GPT；仅用户明确要求时由子 agent 协助 | 需要整体判断和较高质量上限 |
| 已定位的局部枚举/字段错误、按确定契约改有限文件、定向测试、机械资料同步 | 低成本执行模型 | 目标清楚、范围可控、结果可检查 |
| 复核基线、集成 patch、语义审查、关键验收及向用户交付 | GPT | 执行者不能自评为最终通过 |
| 很短且强依赖当前上下文的修改 | GPT 直接完成 | 打包和协调可能比直接做更昂贵 |

用户请求拆分后，只有在根因、目标、编辑范围和验收已清楚时才形成可交接任务。一个 task 表达一个可以独立接受或退回的结果；按文件数量机械切碎同一业务事务会增加成本和风险。

## 文件协议

```text
tmp/agent-handoffs/<batch-id>/
  README.md                     当前会话的交付入口与并行/集成顺序
  <task-id>/
    TASK.md                     执行指令：目标、上下文、边界、交付、升级
    ACCEPTANCE.md               事先定义的验收矩阵、命令、预期与限制
    manifest.json               状态、模式、所有权、依赖、模型档位
    BASELINE.json               HEAD/分支、创建时文件存在性和 SHA256
    RESULT.md                   创建时 NOT_STARTED；执行者填写实际结果
    evidence/                   相关检查输出，避免整份日志反复进会话
    changes.patch               相对包基线的增量补丁，有代码变更时回传
```

长期模板在 `templates/agent-handoff/`，临时包被 Git 忽略。跨机器需要先交付明确的代码副本/授权源码快照，再交付任务包；本机路径和哈希无法让另一台机器自动获得文件。必要时向任务包附允许文件的基线副本，主模型仍保留完整原始差异用于集成。

manifest 中 ready 只表示任务包已完成，不表示已投递、已执行或已验收。BASELINE 记录真实脏文件内容的哈希，而不只是 HEAD；现有未提交修改的基线副本或 patch 应保留在本地。不要把凭据、真实学生数据或整个聊天记录放入包。

`allowed_edit_paths` 仅限定仓库源码/测试增量，回传材料按 `result_artifacts` 在任务目录中写入 RESULT、changes.patch 和 evidence。TASK/ACCEPTANCE/验收脚本/BASELINE 保持主模型管理；执行者通过 RESULT 报告 submitted/blocked，manifest 状态由 GPT 或控制器更新。

## 操作流程

1. **确认用户请求与 GPT 分析**：没有用户明确的拆分/任务书请求时，由 GPT 直接完成，不进入打包流程。收到请求后核对需求、代码、根因和适合交接的范围；复杂/高要求内容由 GPT 写。
2. **GPT 准备任务包**：记录相对路径、HEAD、分支、实际文件哈希；明确 allowed_edit_paths、must_read、依赖和验收。已有任务成果需要作为输入，不让执行者重新调研一遍。
3. **在当前用户会话交付**：给批次入口、每个 task 的目标、复杂度、路径和执行/验收命令。状态保持 ready，清楚告知哪些还需手动投递。
4. **投递并认领**：默认用户复制 TASK.md 的入口提示给第三方工具，并提供对应仓库副本。记录实际产品/模型、工作目录和 claimant；未配置不凭空调用外部工具。自动模式由未来明确配置的适配器消费同一 manifest，不直接执行任务包里的任意字符串命令。
5. **执行**：先核对基线与现有差异，只读必需材料；先跑定向失败用例，再修改允许文件、复跑并回传。遇到基线漂移或合同变化先 blocked，不自行清理工作区或补做高风险决定。
6. **回传**：提交相对基线的 patch 和 RESULT，列出文件、实际命令/工作目录/退出码、证据路径、未验证和阻塞；状态 submitted。无改动检查任务写明没有 patch。
7. **GPT 验收与集成**：只读接收结果，先看基线/范围，再审查语义并独立重跑必要检查。拒绝的是具体增量，不覆盖用户已有修改；修改内容发生冲突时由 GPT 解决和复验。
8. **归档与统计**：GPT 标记 accepted/rework/blocked，记录实际模型、时间和可得到的用量；任务结束后有复用价值的经验写入项目资料，不把临时任务上下文塞回 AGENTS.md。

## 并行与所有权

只有用户明确要求多个子 agent 协作时才启动并行，不能依据历史许可主动调用。并行必须带来独立产出。内置 subagent 受当前工具支持和实际并发上限约束；第三方并行依赖用户启动的会话或获明确授权的已配置适配器，不等同于内置工具。

- 默认最多安排 3 个执行任务同时进行，实际数由可用并发额度、文件所有权和成本决定；用户可调整。不为达到并发数硬拆任务。
- 优先独立 checkout/副本，携带实际脏基线，返回补丁。不能将一个只有 HEAD 的新 checkout 当成含本地未提交功能的等价副本。
- 必须共享工作区时，各 task 编辑清单互斥；依赖文件可以共读，不能两个执行者改同一测试文件、API helper、锁文件或 schema。
- 每个 task 只有一个 claimant。人工模式由用户/GPT 记录认领；自动模式需要原子认领/租约和超时处理，不能靠两个进程各自覆盖 JSON 实现锁。
- 共享文件或接口改动由 GPT 或指定唯一 owner 处理；其他任务暂存 patch，按 manifest 的依赖和集成顺序进行。无编辑范围外的“顺手修复”。
- accepted 必須基于集成后的实际代码检查，而不是多个单独 patch 的各自通过；相互影响的关键行为追加集成检查。

## 验收规则

验收矩阵由 GPT 在下放前写明：输入场景、期望行为、验证方式、命令/工作目录、成功条件和平台限制。测试、格式、类型、构建与业务行为分别判断，不用截图或一句“全部通过”代替证据。

执行者自报的 PASS 只是 submitted 的材料；只有 GPT/用户可以确认 accepted。本项目有既有失败，任务包列出基线与本次阻塞条件；执行者不用修复整个仓库，也不能把未跑、跳过或超时写成通过。暂时没有 MySQL/真机环境时，写明接受范围仅为局部离线结果，不能升级成整套产品验收。

按基线比较本次增量，检查既有脏文件和范围外文件是否变化。日志用虚构/脱敏数据，证据仅保留相关输出；补丁要能在原基线上审阅，不能依赖执行者单机隐藏改动。

## token 与成本管理

- TASK 只携带解决本任务所需信息，正文默认控制在约 1500 字内（代码/测试附件另计），确有需要可以扩展。
- 传路径、接口、最小失败例和预期，避免完整历史、多份重复文档和所有技能同时加载。按需加载与任务有关的技能；外部平台先确认是否已安装，必要规则直接摘要到 TASK。
- 执行模型选择记录在 RESULT，而不将当前所谓“最便宜型号”永久写死。输入/输出 token、费用和币种无法获取时填 null，不能推算为已测值。
- 记录打包/执行/验收/返工的总成本，再判断是否值得继续下放。并行执行通常会增加总调用量，不能仅因墙钟时间减少就声称 token 节省。
- 范围扩大、需要权限/事务判断立即升级；连续两次定向验收失败交回 GPT。减少重复轮询和来回沟通，避免低价模型无限试错反而更贵。
