# 测试运营期教职工临时工号

## 范围与身份边界

后台命令从已确认导入的有效课表和行政班责任文字提取候选；还可直接读取一份班级责任表，因此责任表因缺少档案暂时无法确认时，不必先伪造真实工号。课表与行政班资料仍走已有导入入口。命令不导入学生，不替代教务资料核对，不增加管理页面。

预建的是 `faculty_staff` 档案，`user_id` 保持空，不创建用户名、密码或管理员角色。教师首次通过微信登录创建受限账号，再以工号和一次性绑定码关联档案；权限仍取决于明确有效的任课和班级责任关系。

临时号形如 `TMP_1_000001`，含学校与稳定档案 ID。`TMP_` 是保留前缀，普通教职工新建和档案导入不得使用。临时号不是密码，不能直接登录 Web；绑定临时档案的普通教师即使已有密码，Web 登录、刷新和既有 Web 会话也须先核对真实工号。既有三类管理员账号仍按原角色登录管理端。系统没有在本次增加教师自行注册或自动开通 Web 密码账号。

新增迁移 `f26a1019s007` 基于 `f26a1019d001`，只为 `faculty_staff` 增加可空 `temporary_staff_no` 和学校内唯一约束，不回填或重写既有业务数据。

## 运行环境

在 `backend/` 使用该发布自己的 Python，加载与目标环境相同的配置。CLI 沿用应用的 `DATABASE_URL`；执行前核对连接目标。`--actor-id` 必须是实际有效的操作者账号，命令实时复核其指定学院 `staff.manage` 权限，不信任传入的角色标签。CLI 只供服务器受控终端运行，不暴露为公共 HTTP 接口。

下例 `100`、`10`、`20`、`300` 均是占位 ID，必须换成目标环境实际 ID。文件保存于私有目录，不放在 Web 静态目录、Git 或共享日志中。Windows 继承目录 ACL；Linux 导出凭证文件权限为 `0600`。

## 1. 提取候选（无正式写入）

```bash
python -m app.cli.staff_onboarding --actor-id 100 --college-id 10 preview \
  --semester-id 20 --responsibility-file /private/责任区.xlsx \
  --output /private/plan.json
```

`--responsibility-file` 可省略，读取已导入行政班的班主任、辅导员文字；仅处理责任关系时可省略 `--semester-id`。文件必须是现有解析器支持的班级责任表，不能含学生花名册。课表按教学班/课程保留来源；外部责任表还保留文件名与行号。

输出 `plan.json` 和 `plan-review.json`；不自动核对。计划绑定学院、操作者、业务日期、学期及人员/课表/任职来源指纹，来源变化或跨日后需重新提取。

## 2. 人工核对

保持 `plan.json` 原样。依据计划中的候选、班级、课程和同名档案提示，编辑 `plan-review.json`，每条来源必须选择一次：

```json
[
  {"key":"替换为第一条来源key","action":"CREATE","person_key":"教师A","home_college_id":"10","distinct_from_staff_ids":[]},
  {"key":"替换为第二条来源key","action":"LINK","staff_id":"300"},
  {"key":"替换为第三条来源key","action":"SKIP"}
]
```

- 明确是同一人时，在相应 CREATE 行填写相同 `person_key`；不同人使用不同值，即使姓名一样。
- CREATE 必须确认归属当前学院。授课学院不等于人员归属；跨院教师应先在其归属学院建档，再明确 LINK。班级责任人仍必须属于本院。
- 存在同名档案时默认拒绝 CREATE；若核对后确认为不同人员，必须把该候选 `matches` 中所有档案 ID 完整填入 `distinct_from_staff_ids`，明确排除已有人员。不能只因姓名相同就 LINK。
- 不完整、歧义或冲突资料可明确 SKIP；没有默认跳过，没有默认同名合并。

```bash
python -m app.cli.staff_onboarding --actor-id 100 --college-id 10 confirm \
  --plan /private/plan.json --review /private/plan-review.json \
  --responsibility-file /private/责任区.xlsx --output /private/result.json
```

如提取时使用外部责任表，确认时必须提供同一来源内容。选中资料全部先校验再写入；任一已有任职冲突会回滚本次档案与任职。任职生效日沿用现有补关联规则（责任从当前业务日起，授课从当前日和学期开始日较晚者起），不会从旧表恢复已结束任职，不追补历史权限。

相同计划与核对结果重复确认返回同一审计回执，不重复建档。结果文件使用独占创建，不覆盖；若数据库提交后结果文件写出失败，用原计划/核对文件和新的输出路径重试，可恢复回执。再次提取后，已有人员应明确 LINK。

## 3. 导出工号与一次性绑定码

从结果的 `staff_id` 选择本院、有效且尚未绑定的档案：

```bash
python -m app.cli.staff_onboarding --actor-id 100 --college-id 10 export \
  --staff-id 300 --staff-id 301 --output /private/教师绑定.csv
```

CSV 为带 BOM 的 UTF-8，列为学院、姓名、档案 ID、当前工号、临时工号、绑定码、有效期 UTC。单元格做公式注入保护。只在文件中出现明文绑定码，数据库及审计只保存摘要/时效，不在终端打印凭证。

有效期沿用 `BINDING_TOKEN_VALID_MINUTES`（默认 60 分钟），请临近发放时签发；过期后用新的文件路径重新导出。新签发不会自动作废其他有效码，沿用现有签发规则。一次码核销后不可再次绑定；已绑定档案不能通过本命令换绑。

文件独占创建，不覆盖旧文件；写入/fsync 失败则凭证回滚，提交失败则移除本次文件。文件系统与数据库不能构成跨介质原子事务：进程被强制终止或机器故障时，应核验导出完整性和数据库状态，必要时重新签发。不要把未完成导出文件发给教师。

## 4. 后续补充真实工号

先核对真实工号与原档案的对应关系，明确使用原档案 ID 和当前版本，不通过姓名自动合并：

```bash
python -m app.cli.staff_onboarding --actor-id 100 --college-id 10 set-real-number \
  --staff-id 300 --lock-version 1 --real-number 000123
```

工号按字符串保留前导零。更新主工号并递增版本，原临时号继续保留供微信绑定核验；`staff_id`、微信账号及任课/责任/历史均保留。已被其他人使用的工号、停用档案、错误版本或覆盖另一真实工号会被拒绝。该命令不会创建 Web 口令，也不会修改管理员账号。

当前不提供批量真实工号映射导入；有数据后可按经核对的对照逐项执行本命令。不要把真实工号名单当作新教职工名单直接导入，否则原有按工号建档的导入规则可能创建另一档案。
