## 发现（按实际影响排序）

### F01 / P1：自习默认时间套用普通课节次，缺少实际时刻确认

位置：[TeachingSchedule.vue](../../apps/admin-web/src/components/academic/TeachingSchedule.vue:563)。早自习默认1—2节，晚自习默认9—10节；打开弹窗也默认1—2节。

按线上现有表，这分别是 **08:10—09:45** 和 **17:05—19:35**。默认值没有读取早/晚自习专用时段，也没有依据实际时间选择。因此管理员直接确认会把自习安排到普通课时间，名称“早自习/晚自习”本身不会改变时间计算。

建议：生成界面选择明确的起止时刻或已发布的自习作息方案，并展示日期和时间预览。复用已有 `CollegeTimeProfile`、教学班 `time_profile_id` 与 `TimeResolver`，避免要求管理员通过“新增第13节”解决早晨时段。

### F02 / P1：自习批量生成未校验节次是否有有效作息，错误延迟到任务生成

位置：[scoped_self_study.py](../../backend/app/modules/academic/scoped_self_study.py:18)、[scoped_write_schemas.py](../../backend/app/modules/academic/scoped_write_schemas.py:65)、[TimeResolver.interval](../../backend/app/modules/academic/time_service.py:296)。

批量入口只检查开始编号不大于结束编号；Schema允许1—60，但生成服务未执行普通课写入口的实际作息解析检查，也未传入/绑定指定作息方案。

**已复现**：在已部署提交的隔离SQLite中，不定义第60节，仍能生成并提交 `60—60` 的早自习课表，接口返回SUCCESS；随后按该教学班解析课次时间，报“正式作息缺少所需节次的起止时刻”。这会造成“生成成功，但课次无法正常下发”的断层。

建议：落库前复用 `_schedule_time`/`TimeResolver`，校验全部实际生效日期和所选方案；有缺失则整批拒绝并返回明确修复入口。时间方案应在生成时明确绑定，不能只凭课程名推定。

### F03 / P1：可以删除仍被正式课表引用的节次，随后课次时间解析失败

位置：[AcademicService.delete_period_definition](../../backend/app/modules/academic/service.py:396)、[删除按钮](../../apps/admin-web/src/views/SettingsView.vue:500)。

后端核对权限、有效学期和记录归属后直接删除，没有查询课程节次引用、后续任务或时间方案影响；前端确认框只有节次号，没有引用和影响预览。课表以整数起止范围引用节次，不存在能自动阻止删除的节次外键。

**已复现**：保留1—2节正式课表，删除第1节仍成功；课表没有被删除，之后解析它的时间即失败。

建议：仍允许管理员管理删除，但先展示引用及影响；先迁移引用或明确处置未来课程/任务，再执行删除。已冻结的历史任务不重写。当前第13节未被引用，不代表其他节次可以无条件删除。

### F04 / P1：恢复作息由前端并发覆盖12条记录，存在部分生效和缺少影响确认

位置：[handleInitDefaultPeriods](../../apps/admin-web/src/views/SettingsView.vue:514)、[单条节次保存](../../backend/app/modules/academic/service.py:340)。

- 标准时间硬编码在Web页面，不是从学校已发布模板取值。
- 使用 `Promise.all` 发12个独立写请求，各自提交；任一失败不会回滚其他已成功请求。
- 只覆盖1—12节，**不会删除第13节**。此前基于截图提出的“可能删除第13节”疑问已排除。
- 没有列出受影响学院、课表或未来任务，也没有生效日期和整体修订确认。未使用已有版本化作息的预览/发布链路。

**已复现**：执行实际前端函数，仅模拟第6个请求失败，其余11个保存均成功，最后页面提示“重置失败”。这时实际状态已经部分改变。

建议：将该操作收敛为学校模板选用/版本预览/确认发布。若保留初始化用途，则明确标为“补齐缺失节次”，禁止静默覆盖已使用配置；需要整批覆盖时由后端提供一个有整体校验的事务入口。

### F05 / P2：截图有三处确定的显示错误

位置：[时段与摘要](../../apps/admin-web/src/views/SettingsView.vue:433)、[时长列](../../apps/admin-web/src/views/SettingsView.vue:900)。

| 项目 | 代码行为 | 实际问题 |
| --- | --- | --- |
| 时段名称及颜色 | 1—4节上午，5—9节下午，其余晚间 | 第13节07:30被标晚间；不读取实际起止时间 |
| 时长 | 写死“45分钟标准学时” | 07:30—07:50实际20分钟；“分钟时长”和教学学时也混用 |
| 全日覆盖范围 | 取按编号排序的首行开始、末行结束 | 出现“覆盖08:10至07:50”，遗漏真实的早晨起点和夜间终点 |

建议：时段按实际时间展示（与课程类型分开）；时长由差值计算，列名改为“时长”；覆盖范围取实际最早开始与最晚结束。编号可保留为业务引用，但展示应能看懂实际时间顺序。不要根据时间标签把普通课自动改成早自习类型。

### F06 / P2：旧节次编辑与新作息版本的校验规则不一致

位置：[旧节次编辑](../../backend/app/modules/academic/service.py:340)、[TimeConfiguration.periods_ordered](../../backend/app/modules/academic/time_schemas.py:76)。

旧入口只检查单行结束晚于开始，允许“第13节早于第1节”，也不检查跨行重叠。版本化入口要求按编号递增且不重叠。

**已复现**：旧入口接受1、2节正常上午课再加13节07:30；相同配置交给版本化Schema时被拒绝。“旧页面保存成功”不意味着能直接选用或发布为新作息版本。单独13—13可正确解析，跨越顺序混乱节次的连续范围也可能被TimeResolver拒绝。

建议：不要放宽新入口的时间顺序校验来迁就旧数据。先明确普通课节次与独立自习方案的引用方式，逐步统一旧入口的校验和迁移提示；不得对已有教学班、导入小节和历史任务直接重编号。

### F07 / P2：节次编辑审计的修改前值记录错误

位置：[AcademicService.upsert_period_definition](../../backend/app/modules/academic/service.py:374)。先给 `pd.start_time` 赋新值，再用它构造 `before`；没有保留原结束时间，`after`也没有记录完整新起止时间。

**已复现**：07:30改为07:40，审计 `before.start_time` 保存的却是07:40。后续无法仅凭这条审计可靠还原真正的修改前状态。

建议：赋值前保存起止时间、编号与学期快照，after记录新值，与更新同事务提交。
