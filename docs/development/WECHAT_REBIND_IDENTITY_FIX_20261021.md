# 微信换绑与学生业务账号归属修复

## 审查结论与定位

报告根因成立：`InspectionAssignment.volunteer_user_id` 和 `InspectionSubmission.volunteer_user_id` 指向用户账号。`IdentityService.student_self_unbind` 清空该账号的 `student_id` 和角色，但保留微信身份指向；之后同一 UID 绑定其他学生，导致业务事实被错误解释为另一个学生。记录仍在库中，并非物理删除。

原方案有条件通过：保留学生业务账号，解绑时将唯一微信登录身份移至无角色、无口令、无学生绑定的新账号。原账号的学号归属、资格、角色、受派与提交事实保持。需同时约束既有账号认领、会话有效性、管理员换绑及并发登录/刷新，不能只替换 `student_id = None`。

## 执行与验收计划

1. 独立数据库复现：微信A解绑学生B、再绑定学生A；微信B凭新绑定码认领学生B。验证待执行/已提交受派与提交仍属于B原UID，A不能看到或提交B的任务。
2. 身份修复在 `identity/service.py`，路由传入真实会话ID以在写事务内复核。微信身份迁移不迁移业务事实，不删除源账号，不复活已撤销会话；目标停用、已占用微信或管理/教工混合身份拒绝自助认领。自助解绑不允许管理员/教工身份借此脱离治理。
3. 认领保持当前微信有效会话的刷新链路，旧JWT因sub/sid不匹配失效；解绑撤销原账号会话。账号锁→会话/微信锁的顺序统一，登录和刷新在锁后复查，防止解绑后又签出旧身份会话。绑定前按ID顺序锁定已知源/目标账号，锁后重新核对目标。
4. 管理员换绑对已有受派或提交历史的UID禁止改学生归属，返回明确冲突；未投入查课业务的既有校验纠错流程保留。
5. 先失败后修复，覆盖整个报告流程、核销一次性、停用/占用/特权账号拒绝、旧令牌撤销、回滚及并发。真实MySQL使用本任务新建的独立测试库，禁止对正式业务库执行测试夹具。
6. 提交与整合远端，部署不含迁移的后端；保留当前Web及其他线上更新。记录源码哈希、配置摘要、数据库版本、健康、匿名拒绝及回退目标。

## 数据处置边界

本轮代码修复阻止后续嫁接；不按姓名、当前微信或猜测批量移动线上历史记录。已经发生的错误归属需要核对审计、原受派身份和时间证据，再另行决定逐项恢复。
