# 每周督查排班管理接口候选

日期：2026-10-25。分支 `future/agent-dev`。本地候选、默认关闭、未部署。沿用[周期排班领域](WEEKLY_INSPECTION_DOMAIN_20261025.md)及迁移头a014，本批没有新迁移。管理页面、常驻周期派发和腾讯云ADP编排仍需实施。

## 边界与授权

新增 `weekly_management.py` 保存登录管理操作及只读结果投影，`weekly_router.py` 提供普通Bearer登录API；不是模型工具接口，也不接受AppId、运行令牌或客户端角色来替代登录。所有接口复用当前数据库中的 `inspection.generate`、`assignment.manage` 及学院／类型／组／班级ResourceScope，不增加一套权限系统。

未建计划时同样检查目标组的当前范围，不能凭A组授权探查B组空计划和状态。类型范围授权须匹配目标组的学期固定／当前发布配置；已有策略可以提供相应历史范围。计划／执行中完整类型、班级及全部任务必须在当前授权内；详情越界404，历史列表过滤不可见记录，不泄露隐藏数量。实际教师身份、学生负责人和跨院授权均由原服务处理，JWT中伪造“超管”不会扩大范围。

新增领域保护：修改、缩小或暂停一份已有计划之前，也要拥有该旧计划的完整范围。只有一个类型权限的负责人，不能通过提交较小的新配置接管原本覆盖多个类型的计划。新计划、新配置及旧配置均按当前真实授权核对。

读操作允许在仍有当前授权的前提下查看已暂停计划、停用组／归档学期的历史。GET不登记到期、不生成任务、不创建或作废草案，也不改写执行状态／审计；原登录依赖仍可能更新会话使用时间。

## 接口

公共前缀：`/api/v1/colleges/{cid}/groups/{gid}/inspection/weekly`。所有操作必带查询参数 `semester_id`。路径与学期ID为正的有符号BIGINT范围，不接受客户端指定运行环境。环境从后端配置取得。

| 方法与相对路径 | 参数／请求体 | 结果 |
| --- | --- | --- |
| GET `/policy` | 无额外请求体 | `plan`或null、学期／组状态、固定DRAFT_ONLY模式 |
| PUT `/policy` | 原WeeklyPlanUpdate严格契约 | 保存后实际负责人、策略版本及配置；新计划current_version=0 |
| POST `/policy/pause` | `{"current_version":1}` | 已暂停策略及递增版本 |
| POST `/due` | `{"current_version":1}` | 当前策略已经到期但未登记的执行；重复登记返回空数组 |
| GET `/executions` | `limit`默认20、最大50；可选`before_id` | `items`摘要与`next_before_id`；不用总数或偏移分页 |
| GET `/executions/{eid}` | 无额外请求体 | 原完整回执及当前核对投影，不重算任务 |
| POST `/executions/{eid}/recheck` | `{"expected_assignment_plan_id":"原UUID"}`，或明确null | 人明确复用原任务重新核对；预期指针变化409 |

全部成功响应沿用原 `success` 外层与requestId，设置 `Cache-Control: private, no-store`。创建策略、暂停、登记到期和重核的JSON拒绝多余字段；负责人、学院／组所有权、环境、任意时间覆盖、自动发布模式均不能混入请求体。

PUT示例（ID须使用当前学院真实可用选项）：

```json
{
  "current_version": 0,
  "enabled": true,
  "first_week": 2,
  "last_week": 18,
  "run_weekday": 5,
  "run_time": "16:00",
  "counts": {"101": 2},
  "course_type_ids": ["201"],
  "require_photo": true,
  "publication_mode": "DRAFT_ONLY"
}
```

`/due`仅登记策略已经到期的下一教学周执行，不会在HTTP请求中运行重抽、排班或云模型。不能将该操作呈现为“已完成自动排班”。窗口仍为上海时区，过周记录MISSED；未来常驻派发将消费相同执行记录，通过受限ADP工作流驱动原业务阶段。重复请求可能返回空数组，客户端通过历史查询找回已登记记录，不重建同周执行。

列表只返回执行ID、目标周、状态／原因、时间／日期、任务数及草案ID，不返回整批人员明细。每个策略最多60个教学周，扫描有界；游标只指向实际可见的已返回记录。

## 草案详情与人工确认

详情保留完整原样本和已有受派覆盖快照，并附加：

- `coverage_status`、`coverage_changes`：说明原跳过受派快照是否仍对应当前受派；不代表草案已发布。
- `assignment_plan_status`、`draft_expires_at`：有真实草案时返回；全量已受派结果没有伪造的草案ID或状态。
- `can_confirm`：本次操作者拥有该原草案、有效期内、组／学期可用、原跳过受派未变化，并通过只读业务核验。该值是读取时点事实，不是之后提交的授权票据。
- `requires_recheck`：草案过期、属于其他负责人、业务修订失效或原覆盖变化时提示人重新核对。
- `publication_result`：草案已由人发布时返回原发布事实；不会重建或替换已发布草案。

只读有效性核验复用原 `_targets`、当前受派对照、`load_snapshot(lock_inputs=False)`、`_revision` 和 `validate_plan`，不调用生成器或写事务。任务版本、分类／组规则、候选成员、授权或负载变化可能使草案失效。明确的业务失效返回原历史详情并标为需重核，数据库／编程错误不会被伪装成校验通过。

另一个管理人员可以查看其授权范围内的结果，但不能取得旧草案所有人的确认权；须明确POST重核，产生属于本次操作者的新草案，旧未发布草案原子失效。断网后重复发送旧 `expected_assignment_plan_id` 返回409，应先GET读取当前结果，不默默使刚生成的新草案再次失效。全部已有受派且指针为null时只重核覆盖事实，不创建空草案。

正式发布继续调用原 `/inspection/assignment-plans/{plan_id}/commit`，传原revision并逐项确认具体警告。该接口仍按当前身份、受派、任务／课程／成员／授权／负载修订及硬约束加锁复核，不能根据先前的 `can_confirm=true` 跳过检查。智能体不获得此发布入口。
