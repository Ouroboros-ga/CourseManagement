# 微信小程序身份流程优化移交说明

日期：2026-10-18
交付状态：建议文档，待小程序开发者实施。此前尝试的本轮小程序、配套后端和接口契约改动已回退；未提交、推送或部署这些改动。

## 1. 业务目的与已确认边界

教职工绑定微信并确认工号后，应直接使用统一的教职工界面，查看本人课程、所管辖责任区的考勤。不能因为沿用学生绑定判断而反复要求教职工绑定学号。

本次移交只优化身份上下文、登录分流、绑定后刷新三个环节。“课程 / 考勤 / 我的”完整页面及其业务功能仍需独立实施，不能将本说明视为这些页面已经完成。

账号沿用当前流程：首次微信登录创建或复用系统账号；工号与一次性绑定码确认教职工身份，将有效档案关联到当前账号。不要求导入档案时预建账号，不因绑定再创建第二个账号，不覆盖已有用户名，不按姓名或手机号自动合并账号。

上述账号时序采用用户后续确认的口径，替代此前统一账号需求（原相对路径：`../product/STAFF_MINIAPP_IDENTITY_REQUIREMENTS_20261018.md`）中“建立档案时配套建立账号”的表述。工号用于确认档案归属，并不等于必须作为账号的登录用户名。

任课教师、班主任、辅导员属于同一教职工的业务任职关系，不分别建号或提供三套身份入口。统一界面不授予学院管理权限；每次业务查询和写入继续由后端核对课程、责任区、生效日期和资源版本。

## 2. 当前可用接口与已知兼容点

以下是本地基线 `b7e0ca1` 中已有的接口；本次仅核对代码，未重新进行线上或微信真机验收。

| 接口 | 请求或返回重点 | 小程序用途 |
| --- | --- | --- |
| `POST /api/v1/auth/wechat/login` | 请求含 `code`；返回令牌及 `need_binding` | 微信认证并建立会话 |
| `GET /api/v1/me` | 业务数据位于 `data`，含账号、角色、权限、`binding_required`、`app_context` | 登录后及身份变化后读取真实上下文 |
| `POST /api/v1/me/staff-binding` | `{staff_no, binding_code}` | 为当前账号核销教职工绑定码并关联档案 |
| `POST /api/v1/me/student-binding` | `{student_no, binding_code}` | 保留学生身份确认流程 |
| `POST /api/v1/auth/refresh` | 小程序通过 JSON 提交 `refresh_token` | 续期后至多重试原请求一次 |

`need_binding`、`binding_required` 保留了旧学生流程的判断口径。纯教职工即使已绑定有效档案，这些字段仍可能为 `true`，因此不能单独据此判断“必须绑定学号”。当前教职工接口通过独立的档案依赖验证身份，不能把这些旧字段理解为所有教职工功能均被禁止。

现有 `/me` 已提供如下 `app_context`，无需等待新增字段才能开展小程序适配：

```json
{
  "modes": ["staff"],
  "default_mode": "staff",
  "administrator": false,
  "staff": {
    "staff_id": "123",
    "staff_no": "001234",
    "name": "示例教职工",
    "college_id": "456",
    "views": {"teaching": true, "responsible": false}
  }
}
```

- `modes` 可包含 `student`、`staff`；双身份当前默认 `student`，无可用模式时默认值为 `null`。
- `staff` 来自有效绑定档案；`views` 是当前任职关系摘要，不是绑定是否成功的标志，也不是具体记录的授权凭证。
- 有效教职工尚未配置任课或责任区时，仍属于 `staff`，两个视图标志可以同时为 `false`。
- `administrator` 表示后台管理身份摘要，不自动添加学生或教职工模式，具体操作仍看有效权限及接口授权。
- 工号、学号和所有 ID 按字符串处理，保留前导零，不使用 `Number` 或 `parseInt` 转换。
- 两个绑定接口返回各自绑定结果，不返回完整身份上下文；成功后需要重新调用 `/me`。

可选后端配合：未来可为 `/me` 补充明确的响应模型，或约定新的统一身份状态字段，以便生成接口类型。此前尝试添加的 `identity_state` 等字段已回退，当前不能依赖，也不应在小程序中假设它已上线。旧兼容字段的调整应另行协调现有调用端。

## 3. 优化一：统一身份上下文

由小程序维护一个共享身份上下文，登录页、首页、“我的”使用同一份 `/me` 解析结果，避免各页面分别根据角色数组猜身份。

建议保存当前账号 ID、可用模式、当前选择模式、教职工摘要、有效权限和加载状态。将“尚未加载”“加载失败”“确实没有业务身份”分开；请求失败不能回退成学生身份或未绑定状态。

身份呈现规则：

| `/me` 返回情况 | 页面行为 |
| --- | --- |
| 只有 `staff` | 进入统一教职工入口，不提示绑定学号 |
| 只有 `student` | 进入学生入口，保留已有学生功能 |
| 同时有两种模式 | 使用该账号此前选择的有效模式；无有效选择时采用服务端默认值，提供切换入口 |
| 无模式，且无管理员身份 | 提供学生或教职工身份确认入口 |
| 无模式，但有管理员身份 | 保留已有管理身份可用入口，不强制绑定学生；需要教职工功能时再确认工号 |
| 教职工有效，但没有任课或责任区 | 显示“尚未分配课程／责任区”，不重新引导绑定，不扩大数据范围 |

模式偏好按账号 ID 隔离，每次刷新后验证它仍在 `modes` 中。不同账号不能继承前一个账号的教职工信息或选择。不要用角色优先级、姓名、称呼或空角色数组来推断“学生”。

## 4. 优化二：登录后按实际身份分流

建议流程：`wx.login → 后端微信登录 → 保存会话令牌 → GET /me → 应用共享上下文 → 按可用模式进入页面`。

`need_binding` 只能作为旧流程兼容信息。登录成功后必须先读取 `/me`，再决定进入学生、教职工或身份确认入口。若读取失败，提供重试，不显示“请先绑定学号”。

身份确认页建议先选择“学生／教职工”，再分别展示“学号／工号”和对应绑定码输入框。学生表单继续使用学生语意；共用登录提示改为“请确认身份”等中性文案。教职工表单明确提示工号，不能把工号填写到学号字段后调用学生绑定接口。

“我的”可以提供添加另一身份的入口。已有可用身份的用户取消添加时应能返回原页面，避免被强制卡在首次绑定流程。此轮不新增账号自动合并、跨账号迁移或自助教职工解绑规则。

## 5. 优化三：绑定成功后刷新身份与页面

学生、教职工绑定统一遵循：`提交对应绑定接口 → 绑定成功 → 清空一次性凭证 → GET /me → 更新上下文与页面 → 导航`。

特别区分两个结果：

- 绑定接口失败：保留可修正的输入并展示服务端错误，不标记绑定成功。
- 绑定接口成功，但 `/me` 刷新失败：明确提示“绑定已成功，身份信息刷新失败，请重试”，只重试读取 `/me`，不重复核销已使用的绑定码。

提交期间防止重复点击。页面再次显示时按需刷新身份；页面隐藏、销毁或已切换账号后，旧请求结果不能覆盖当前界面。退出登录后清理当前账号的临时身份数据。

请求层继续保留串行刷新令牌、原请求至多重试一次的约束。增加会话代次或等效校验，使旧会话的 `/me`、续期成功、401 失败结果不能恢复旧账号，也不能清空新账号的会话。模式选择发生变化时，较早的身份读取也不能无条件把用户切回默认模式。

## 7. 验收场景

1. 新微信用户可选择学生或教职工确认身份，表单调用正确接口。
2. 已绑定纯教职工即使旧绑定标志为 `true`，也不会被要求绑定学号。
3. 无任课、无责任区的教职工显示分配状态，不被判定为未绑定。
4. 学生已有功能保持可用；双身份切换、重进页面后保持当前账号的有效选择。
5. 管理员单身份账号不会被强迫绑定学号，也不会自动得到教职工身份。
6. 绑定成功立即刷新；绑定成功但刷新失败时，只重试 `/me`，不重复提交绑定码。
7. 退出后重登或切换账号，旧请求和旧续期响应不能污染新会话。
8. 添加身份中途取消能回到原有页面；未获授权的课程、责任区和管理接口仍由后端拒绝。
9. 工号前导零、大整数 ID、绑定码失效及接口错误有正确处理。
